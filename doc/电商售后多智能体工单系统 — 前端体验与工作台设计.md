# 电商售后多智能体工单系统 — 前端体验与工作台设计（Frontend Experience & Workbench Design）

> **定位**：本文件描述系统的**前端产品与工程设计**，回答"不同角色看到什么、操作什么、如何保证操作安全"，不描述 AI 编排内部流程（见《项目架构说明书》），也不描述服务端部署拓扑（见《生产环境架构设计》）。
> **边界声明**：本文件是**设计文档**，不是已实现代码，也不是已通过验收的线上界面。文中出现的接口路径和事件格式属于**建议契约**；在《生产基线与验收测试》完成联调验收前，不得被前端代码当作已冻结接口。
> **设计取向**：本系统不是营销官网，也不是演示聊天框，而是面向**客服工作台、审批中心、客户服务会话、租户管理与审计**的一体化后台产品；第一屏应直接进入可用工作界面。

---

## 一、目标与原则

### 1.1 产品目标

1. **高效处理**：客服可在同一会话内看到对话、订单/物流、政策依据、记忆事实与审批状态，减少跨页面抄录。
2. **安全审批**：退款、退货、改址三类敏感操作必须由审批中心承接，界面不得提供绕过审批的快捷执行入口。
3. **可信呈现**：AI 回复与工具结果区分展示，展示引用的政策依据与来源，不把"推理过程"包装成事实。
4. **多租户隔离**：每个登录用户只能看到其服务端授权租户内的数据，前端不承担跨租户访问能力。
5. **异常可交接**：降级、转人工、审批超时、模型不可用等状态都必须在界面可识别，并且能保留上下文交给人工。

### 1.2 设计原则

| 原则 | 落地要求 |
|---|---|
| **服务端权威** | 租户、用户、角色、资源归属只信服务端 `TenantContext`；前端任何字段不得改写身份。 |
| **无乐观成功** | 敏感写操作未收到服务端 `completed` 前，不显示"已退款/已退货"；重复提交由 `operation_id` 幂等。 |
| **证据优先** | 政策引用展示文档标题/摘要/置信度；不展示隐藏提示词、完整思维链或未脱敏原始 PII。 |
| **可扫描布局** | 列表、筛选、状态徽标、表格和信息密度优先于大块说明文案；不使用营销式大 Banner。 |
| **失败可恢复** | SSE 断线有重连提示，敏感操作中断必须转人工并保留审批上下文，不得让用户无休止重试。 |
| **最小化泄露** | 404/403 不区分"租户/资源/权限"细节；URL、缓存、日志、浏览器存储均避免 PII。 |

## 二、角色与前端能力矩阵

### 2.1 角色来源

角色由服务端 `tenant_memberships` 与 RBAC 决定，前端只渲染当前角色可见菜单和按钮；`platform_admin` 是平台级独立能力，**不进入租户会话、审批或客服工作台**。

| 角色 | 主要界面 | 敏感操作 | 说明 |
|---|---|---|---|
| `customer` | 客户服务会话、我的工单 | 无直接执行权 | 可发起退款/退货/改址请求，但审批由他人完成 |
| `agent` | 客服工作台、会话历史 | 不可独自审批敏感写 | 可查看本租户被授权工单、执行人工介入/转人工 |
| `approver` | 审批中心 | 可审批授权范围内的敏感写 | 必须看到审批依据和二次确认 |
| `admin` | 全部租户管理界面 | 租户成员、策略、审计查看 | 可配置本租户审批人、成员与策略 |

> 前端菜单应随角色变化而隐藏/禁用，但**安全边界必须由后端强制**；前端隐藏只用于体验，不用于授权。

## 三、信息架构

### 3.1 顶层导航（登录后）

建议使用紧凑侧边栏，按角色显示：

1. **客服工作台**：会话/工单列表、会话详情、转人工、搜索、筛选。
2. **审批中心**：待审批、已审批、审批记录。
3. **会话历史**：按租户/客服/客户/时间查询。
4. **审计与可观测**：租户管理员查看审计记录、任务状态；普通客服仅查看本人操作记录。
5. **成员与设置**：仅租户管理员/审批人可访问，用于管理本租户成员、角色、策略。

> 不建议把"记忆图谱"或"模型配置"直接暴露为普通导航；它们属于内部运维/调试能力，应放在受控管理区，避免用户误以为可编辑模型知识。

## 四、核心页面设计

### 4.1 客服工作台（主界面）

建议采用三栏布局，桌面优先，移动端切换面板：

| 区域 | 内容 | 交互要点 |
|---|---|---|
| 左栏：会话/工单 | 搜索、筛选（状态/意图/租户/负责人）、列表、创建会话 | 点击会话切换详情；新会话由服务端生成 `thread_id` |
| 中栏：对话工作区 | 消息流、AI 回复、输入框、SSE 状态、暂停/取消/重连 | 流式输出实时显示；节点状态可收起 |
| 右栏：上下文 | 订单信息、物流轨迹、政策/知识引用、记忆事实、审批状态、操作时间线 | 引用可点击查看来源；敏感操作区高亮 |

**中栏关键状态**：

| 状态 | 展示 | 交互 |
|---|---|---|
| `streaming` | 输出光标、节点进度 | 可取消本次生成 |
| `awaiting_human_approval` | 显示"等待审批"和审批编号 | 客服可补充备注，不能代替审批人点击"通过" |
| `degraded` | 显示降级模式（查询/政策） | 说明本次为受限模式，不承诺写操作 |
| `handoff_required` | 显示"需要人工处理" | 保留上下文，提供转人工按钮 |
| `error` | 错误码与可读说明 | 允许重试读类请求；写类请求引导转人工 |

### 4.2 审批中心

审批中心是独立的敏感操作入口，不是聊天窗口的附属按钮。审批卡片必须包含：

| 字段 | 必要性 |
|---|---|
| `approval_id`、`operation_id` | 必须展示，用于追踪 |
| 操作类型（退款/退货/改址） | 必须展示 |
| 金额、订单号、客户上下文摘要 | 退款/退货必须展示；地址变更应只展示脱敏地址与变更字段 |
| 政策依据与来源引用 | 必须展示，帮助审批人判断 |
| 发起时间、关联会话/客服 | 必须展示 |
| 审批人、审批时间、审批结果 | 已审批记录必须展示 |

**交互规范**：

- 点击"通过/拒绝"后先出现**二次确认弹窗**，拒绝时必须填写原因。
- 提交后按钮进入 `submitting` 状态，防止双击产生重复审批请求；重复提交应被服务端 `operation_id` 幂等拒绝/重放。
- 审批结果以服务端返回为准，不使用本地乐观更新作为最终状态。
- 若审批超时、会话过期或网络失败，界面显示"状态未知"，提供查询/刷新，不得提示用户直接重发敏感操作。

### 4.3 客户会话视图

客户登录后进入简洁会话界面，可查看：

- 当前会话状态与客服是否在线；
- 已提交工单/退款/退货/改址请求的处理状态；
- 服务端返回的政策引用（可展开原文）；
- "需要人工处理"时显示等待提示，不暴露内部推理。

客户界面不应出现：

- 审批人操作、租户管理、内部系统切换；
- 完整模型思考、工具调用明细、记忆图谱原始结构；
- 其他客户的订单/会话/地址等数据。

## 五、会话与流式通信（前端状态模型）

### 5.1 冻结 API 契约（设计态，待实现验收）

本节与《生产环境架构设计》§3 使用**同一份冻结口径**。它是前端 Mock、类型定义、后端 OpenAPI 和契约测试的依据，但当前项目尚无可运行接口，不能把“冻结”表述为“已联调”或“已生产验收”。

**AI 流只有一个入口**：`POST /api/chat`，返回 `text/event-stream`。不使用 JSON `ChatResponse`，不提供 `/ws/chat` 或第二条聊天 API。

    # 发起新一轮图执行
    {"mode":"start","thread_id":"<server-issued UUID>","client_request_id":"<UUID>","message":"<text>"}

    # 仅续传既有流；请求头必须含 Last-Event-ID
    {"mode":"resume","stream_id":"<opaque stream id>"}
    Last-Event-ID: <last received SSE id>

- `start` 必须携带 `thread_id`、`client_request_id`、`message`；前端不得发送 `tenant_id` 或用户 ID。`client_request_id` 在同一次用户提交中保持稳定，以便服务端去重。
- `resume` 的 body 只能携带 `stream_id`；前端从已持久化的该流最后一个事件 ID 写入 `Last-Event-ID`。它只获取漏掉的事件和继续订阅，不能重新执行图、工具或写操作。
- 第一帧必为 `accepted`。前端收到后持久化 `stream_id`；后续按 `(stream_id, id)` 去重，避免重放时重复追加 token 或重复更新节点状态。

所有 SSE 帧都严格包含 `id`、`event` 和单行 JSON `data`；`event` 只能是下表六种，不能依赖匿名 `data:`、`message`、`ping` 或 LangGraph 原始事件：

    id: 17
    event: accepted
    data: {"stream_id":"s_...","thread_id":"...","client_request_id":"...","mode":"start"}

| 事件 | 前端最小处理 | JSON data 最小字段 |
|---|---|---|
| `accepted` | 保存流标识和恢复游标 | `stream_id, thread_id, client_request_id, mode` |
| `token` | 追加增量文本（按事件 ID 去重） | `delta` |
| `node` | 更新可见进度，不展示内部提示词 | `name, status, progress?` |
| `approval_required` | 打开/刷新审批状态，不显示写入成功 | `approval_id, operation_id, status` |
| `done` | 结束该流并刷新相关资源 | `status, final_response?, operation_id?` |
| `error` | 展示受控错误；按资源状态恢复而非重放写请求 | `code, message, retryable, operation_id?` |

**统一 REST 资源**（所有路径使用 `/api` 前缀，服务端根据 `TenantContext` 授权）：

| 方法与路径 | 前端用途 |
|---|---|
| `POST /api/sessions` | 创建会话，取得服务端生成的 `thread_id`。 |
| `GET /api/sessions` | 会话/工单列表。 |
| `GET /api/sessions/{thread_id}`、`GET /api/sessions/{thread_id}/messages` | 会话详情、摘要和消息历史。 |
| `GET /api/approvals`、`GET /api/approvals/{approval_id}` | 审批列表、审批详情和关联 `operation_id`。 |
| `POST /api/approvals/{approval_id}/decision` | 明确的人工审批决定；提交后以服务端操作状态为准。 |
| `GET /api/operations/{operation_id}` | 敏感业务操作的权威结果查询。 |

前端不能把 Vercel AI SDK 默认 `useChat` 直接接到本协议：其默认数据流格式并不等同于上述自定义 SSE 字典。实现时使用 `fetch` + SSE parser，或编写 SDK 的自定义 transport/协议适配器；`EventSource` 不能发送规定的 POST body。

### 5.2 前端连接状态机

```text
idle
  └─ send() ─> connecting
                 └─ connected/streaming ─> idle | done
                  └─ network_lost ─> resume_connecting (stream_id + Last-Event-ID)
                  └─ error / stream_expired ─> 刷新会话、审批或操作状态
                  └─ approval_required ─> 审批中心
```

约束：

- 取消读取使用 AbortController；它不能被解释为已取消服务端的敏感业务动作。
- 断线后的唯一自动网络动作是 `resume`，且必须带 `stream_id` 与 `Last-Event-ID`。禁止用原 `message`、`thread_id` 或审批 body 自动重发 `start`。
- 退款、退货、改址等敏感写不因断线、刷新或超时重放。收到 `approval_required` 后仅由用户显式调用审批决定；若结果未知，先 `GET /api/approvals/{approval_id}`，再用 `GET /api/operations/{operation_id}` 确认。
- 页面刷新后如存在未决审批或操作，应先拉取会话、审批和操作状态再恢复 UI，不直接恢复“正在执行”或“已成功”的乐观状态。

## 六、多租户与前端安全

### 6.1 租户上下文

前端通过登录后的会话/令牌获得当前租户展示名，但**不接收、不组装、不提交** `tenant_id` 表单字段。所有身份相关请求头/字段由前端框架统一从令牌派生，后端校验。

前端展示约束：

- 可在顶栏显示当前租户标识，但不允许用户输入/切换租户 ID；
- 如需"切换租户"能力，必须是服务端受控会话切换，不能由客户端修改请求体；
- 资源 URL 中只放不透明 `thread_id`、`approval_id`，不拼接租户名或用户 ID。

### 6.2 数据脱敏

| 字段 | 展示规则 |
|---|---|
| 客户手机号/邮箱 | 默认脱敏（如 `138****8000`），需显式授权展开 |
| 收货地址 | 审批卡片默认只显示变更摘要与脱敏地址，完整地址按角色授权 |
| 订单金额 | 审批/财务角色可见；客户仅见与本人订单相关金额 |
| 日志/审计 | 不输出完整 PII，默认聚合；详情访问有审计 |

### 6.3 错误呈现

- 服务端返回 `403`/`404`/`410` 时，界面统一展示"资源不可用或无权限"，不区分资源是否存在。
- 网络错误不携带服务端详情到控制台日志。
- 前端日志不得包含完整消息明文、地址、支付信息或令牌。

## 八、响应式、可访问性与体验底线

### 8.1 响应式

- **桌面（≥1280px）**：三栏工作台；审批中心支持表格与详情抽屉。
- **平板（768–1279px）**：工作台变为可折叠抽屉或纵向堆叠，审批卡片优先显示核心字段。
- **手机（<768px）**：客户会话/工单跟踪为主；审批与管理功能提示"请在桌面端完成"，不提供危险的低密度审批布局。

### 8.2 可访问性

- 流式输出区设置 `aria-live="polite"`，避免朗读每个 token；
- 所有图标按钮提供 `tooltip`/`aria-label`；
- 颜色对比度满足 WCAG AA；不使用颜色作为唯一状态标识；
- 键盘可完成：切换会话、输入消息、取消生成、审批二次确认。

### 8.3 体验底线

- 任何"等待/处理中"状态都给出明确文案，不出现空白转圈；
- 审批操作不可因双击/重复按键产生重复请求；
- 会话列表与审批列表在数据变化时保持稳定顺序，防止跳变；
- 不将 AI 输出直接覆盖为唯一事实；政策引用可展开原文。

## 九、部署与运行约束

### 9.1 前端运行环境

- 若使用 Next.js SSR/Route Handler，需自建 Next.js runtime（或 standalone output），由 Nginx/Ingress 反向代理，不能只靠静态 CDN。
- 若明确采用静态导出，则仅支持前端无服务端依赖的能力；SSE/审批等仍需要后端 API 地址配置。
- 生产环境前端、API、worker 独立部署，前端通过内部域名访问 API，不在浏览器直接暴露数据库。

### 9.2 配置安全

- 后端 API Base URL、SSE 端点通过服务端环境变量注入；
- 浏览器环境不存后端密钥、模型密钥、数据库连接；
- 前端构建产物不含明文租户管理接口密钥。

## 十、验收与测试（前端）

前端验收作为《生产基线与验收测试》的一部分，至少覆盖：

1. **角色可见性**：customer/agent/approver/admin 分别只能看到授权菜单与操作。
2. **双租户隔离**：两个租户使用同名字段时，工作台/审批/历史不串数据。
3. **敏感写失败 UI**：无权限、超时、审批失败、重复提交时，界面不显示"成功"。
4. **SSE 断线恢复**：读类流中断后重连不重复渲染；写类请求状态查询正确。
5. **重复点击审批**：双击/多标签页提交只产生一次业务执行。
6. **PII 脱敏**：客服、客户、审批人视角对敏感字段的可见范围正确。
7. **移动端基本可用**：客户流程可在手机完成；审批管理在桌面可用。
8. **租赁服务器预发布**：前端与后端真实网络联调、HTTPS、断线、审批流转均需记录验证证据。

> 在本设计包中，以上验收项均为**待执行**；任何截图/演示都不等同于线上生产验收。

## 十二、设计说明

> "前端不是简单聊天页，而是客服工作台与审批中心：会话、订单、政策证据、记忆事实和审批状态集中在同一工作区；敏感写操作只走审批中心，按钮不会乐观显示成功；多租户边界和 PII 脱敏由服务端决定，前端只负责清晰呈现。流式通信只用 POST SSE：断线以 stream_id 和 Last-Event-ID 续传，写类异常以 operation_id 查询并转人工。工程上采用 Next.js + Ant Design 和自定义 SSE parser/协议适配器，生产自托管，不依赖 Vercel 平台。"

**高频追问应答**：

- "前端能不能自己判断租户？" 不能。前端只展示当前授权租户，身份与归属全部由服务端 `TenantContext` 决定。
- "审批按钮为什么不直接放在聊天框？" 审批是独立受控业务动作，需要依据、二次确认和审计，独立审批中心更清晰且不易误点。
- "AI 回答怎么保证可追溯？" 前端展示来源引用，但来源检索、幻觉检测和权限过滤都由后端完成，前端不自行解释引用。
- "为什么现在不先写页面？" API 设计契约已冻结，但当前仍无可运行后端；前端实现应先完成 Mock 与前后端契约测试，再进入真实 SSE、审批和多租户联调。
