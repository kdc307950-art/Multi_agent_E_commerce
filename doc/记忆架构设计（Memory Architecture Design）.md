# 记忆架构设计（Memory Architecture Design）

> **项目**：电商售后多智能体工单系统（E-commerce After-Sales Multi-Agent Ticket System）
> **定位**：本文档是「项目架构说明书」的记忆层专项补充，聚焦**长期记忆（Long-term Memory）** 的选型与接入设计。
> **核心结论**：长期记忆采用 **Graphiti（开源时序知识图谱框架）+ Neo4j（社区版）** 的自托管设计。Graphiti 可独立获取和部署；自托管环境必须显式关闭其匿名遥测并限制未经批准的网络出口。但本项目尚无可运行代码，Graphiti、Neo4j 和本地 OpenAI 兼容模型端点的联调只能标记为**待验证**，不能写成已完成的生产集成。

---

## 1. 为什么需要记忆

当前系统已有三层状态，其中长期记忆为新增设计：

| 记忆层 | 存什么 | 现状 | 载体 |
|---|---|---|---|
| **短期记忆**（当前工单会话） | 对话历史、意图、工具结果、审批状态 | ✅ 设计已定义 | LangGraph 检查点 + `tenant_id` + `thread_id` |
| **知识记忆**（政策/规则） | 退货/退款/物流政策、FAQ | ✅ 设计已定义 | Agentic RAG；知识库、检索与缓存带 `tenant_id` 作用域 |
| **长期记忆**（按租户/用户隔离） | 明确业务事实：订单、偏好、地址、历史工单 | 新增设计 | **Graphiti（时序图谱）+ Neo4j**，实体和事实均带 `tenant_id` |

售后工单的核心痛点是：**用户是"连续的人"，不是"一次性工单"**。用户搬家、换地址、重复咨询同一问题，都要求系统记得"这个用户是谁、之前发生过什么、当时是什么样"。没有长期记忆，agent 每单都从零开始。

> **分工澄清**：政策问答仍走 **Agentic RAG（Milvus）**；**图谱（Graphiti + Neo4j）只做"用户画像记忆层"**，两者不冲突、不同层。

## 3. 选型论证：为什么选 Graphiti（时序图谱）

### 3.1 需求拆解（从项目真实场景反推）

1. 核心记住可验证的**用户级事实**（订单、地址、偏好、历史工单）
2. 事实**会随时间变化**，需要回答"当时是什么样"（地址、会员等级、订单状态演进）
3. **必须完全自托管 / 开源**，数据留在项目方控制的服务器、网络和备份边界内（可为自管机房或项目账户下的租赁 IaaS；律所/审计/生产合规导向），并关闭未经批准的匿名遥测/外联
4. 具备**独立记忆框架**形态
5. 答辩可讲清架构、有**差异化亮点**

### 3.2 候选对比矩阵

| 需求 | Mem0 | Letta | **Graphiti** |
|---|---|---|---|
| 用户画像/偏好 | ✅ | ✅ | ✅ |
| **会变 + 回溯"当时是啥"** | ⚠️ 需额外时序建模 | ⚠️ 需额外时序建模 | ✅ 原生面向时序事实；仍需做项目集成验证 |
| 自托管/开源 | ⚠️ 偏云，OSS 自托管重 | ✅ | ✅ **Apache-2.0** |
| 独立框架 | ✅ | ✅ | ✅ |
| 面试差异化 | ⚠️ 名气普通 | ⚠️ 概念新但难落点 | ✅ **最高**（"哪条事实何时为真"） |

> **选型依据**：需求确认中明确“事实会变、要回溯当时”。时序知识图谱与此直接匹配，Graphiti 是当前优先候选；但“只有它能满足”是过度结论，纯 Neo4j 手动时序建模等方案也可实现同一能力，代价是需要自行承担抽取、有效窗口和检索编排。本项目选择 Graphiti 是为了减少这部分自建工作，而不是宣称不存在替代路径。

### 3.3 为什么不用 Mem0 / Letta（客观陈述）

- **Mem0**：抽取式事实记忆 + 去重覆盖。用户搬家后就更新成新地址，旧地址消失，无法回答"上个月他地址是啥"。引用其对外分数时须区分"官方平台自报"与"独立评测"口径，避免误导。
- **Letta**：OS 式虚拟内存（MemGPT 延续），强在 agent 自管上下文、长时运行。但它解决的是"别把上下文撑爆"，**不是"用户画像随时间演进怎么查历史"**，与本项目核心诉求错位。

> **一句话论点**：工单画像的关键不是"记得"，而是"**某条事实在哪个时间区间为真**"。这只有**时序知识图谱**真正能做到。

## 4. 长期记忆架构设计（Graphiti + Neo4j）

### 4.1 时序知识图谱原理

Graphiti 与"静态知识图谱/RAG"的本质区别：**每条事实带"有效期限戳（validity window）"**，支持：

- **时序追踪**：记录"何时为真、何时失效"（`valid_from` / `valid_to`）
- **数据溯源（provenance）**：每条事实可回到来源（会话、文档、工单）
- **增量更新**：无需整图重算即可追加事实
- **Schema 灵活**：支持预设 ontology + 从数据自动学习 ontology

> Graphiti 为 Apache-2.0 开源时序图谱框架，可自托管；本项目不依赖 Zep Cloud。Graphiti 默认匿名遥测必须在部署清单和运行环境中显式以 `GRAPHITI_TELEMETRY_ENABLED=false` 关闭，并通过出网策略验证。实际接入仍须验证锁定版本、Neo4j 驱动、本地 embedding/LLM 端点、租户过滤和故障恢复，验收完成前不得把“可自托管”扩展表述为“本项目已生产验证”。

### 4.2 数据模型（面向售后工单，只存明确事实）

```text
实体 (Entity)                         关系/事实 (Fact)
────────────────────────             ────────────────────────────────
(:Tenant {tenant_id})   ──owns──▶     :User（同一租户内 user_id）
:User (tenant_id, user_id) ──prefers──▶ :Preference（偏好：数码类/退货运费……）
:User                   ──lives_at──▶ :Address（地址，带有效窗口）
:User                   ──has_shipped_count──▶ :Counter（历史退货/退款次数，客观计数）
:Order (tenant_id, order_id) ──status──▶ :Status（delivered/returning/refunded）
:User                   ──opened────▶ :Ticket（工单历史）
```

每条「事实」记录：**主体 → 谓语 → 客体 + 有效窗口 + 来源**。例：

```json
{
  "tenant_id": "TENANT-001",
  "subject": "USER-001",
  "predicate": "lives_at",
  "object": "北京市朝阳区XX路XX号",
  "valid_from": "2025-01-15T00:00:00Z",
  "valid_to": null,
  "source": "ticket TKT-20260115-002"
}
```

当用户 2026-06 变更地址，写入新事实并把旧事实 `valid_to` 置为 `2026-06-01`，保留"当时"的历史。

> **不存主观风险标签**：原型**不记录**如"维权成瘾""高风险用户"等主观画像标签，也不基于这些标签自动做退款/退货拒绝。只保留可验证的**客观业务事实**（订单、地址、工单、历史计数）供人参考，由客服/审批人结合政策判断。

> **多租户隔离**：所有 Neo4j 节点、关系、Graphiti episode、事实 metadata、向量 embedding 与检索请求都必须带 `tenant_id`。查询条件必须先限定 `tenant_id` 再按用户/订单筛选；禁止用全局 `user_id` 或 `order_id` 查询。建议创建复合唯一约束，例如 `User(tenant_id, user_id)` 与 `Order(tenant_id, order_id)`。

### 4.3 图谱能回答的具体场景

> 用户说："我之前买的那个耳机和现在这个充电器不兼容。" 系统通过图谱遍历 `User → 历史订单 → 商品 → 兼容关系 → 当前订单` 这条多跳路径——这是纯向量检索（政策 RAG）做不到的，体现图谱记忆层的价值。

### 4.4 Graphiti + Neo4j 自托管组成

```text
┌─────────────────────────────────────────────────────────────┐
│  Graphiti（时序图谱引擎，Python，Apache-2.0）                  │
│  ├─ 图数据库后端：Neo4j（社区版，自托管，Bolt 协议）           │
│  ├─ Embedding（本地或 OpenAI 兼容模型）                       │
│  └─ 元数据存储（Postgres / SQLite）                           │
│  └─ 匿名遥测：`GRAPHITI_TELEMETRY_ENABLED=false` + 出网限制    │
└─────────────────────────────────────────────────────────────┘
```

**为什么选 Neo4j**：图库生态成熟、Cypher 直观、社区版免费可自托管、Graphiti 支持 `bolt://`。用户画像 + 时间窗 + 关系路径的查询用 Cypher 最顺手。

**Neo4j 自托管要点**：使用锁定版本镜像并挂载数据卷；Bolt 默认 `7687`、HTTP 默认 `7474`。生产部署须明确备份、恢复、索引与查询超时策略，不能仅以容器能启动代替可恢复性验证。

### 4.5 接入流程

**写入（异步，不进同步主链路）**：在 `generate_response` 节点后，把本单可验证的用户事实（偏好、新地址、历史工单、客观计数）连同服务端 `tenant_id` 异步喂给 Graphiti 增量建图，不占 <10s 响应预算。任务消费前再次校验租户状态，停用/删除中的租户不得继续写入。

**检索（意图分类前注入）**：在 `classify_intent` 前，按 `tenant_id + user_id` + 当前时间窗拉取该租户内用户的**当前画像**注入 system prompt；需要时做**历史回溯**。知识检索同样必须使用当前 `tenant_id` 的 collection/partition/filter，不能回退到全局知识池。

## 5. 与现有系统的接线（代码示意）

> 接入示意，Graphiti 具体 API 以官方文档为准。

```python
# ① 检索注入：意图分类前拉当前画像
from src.memory.recall import recall_user_profile

def classify_intent_node(state: AgentState) -> dict:
    profile = recall_user_profile(
        tenant_id=state["tenant_id"], user_id=state["user_id"], as_of=None
    )
    state["context_user_profile"] = profile
    return {"intent": ..., "confidence": ...}


# ② 写入：回复生成后异步抽取用户事实并增量建图
def write_memory_node(state: AgentState) -> dict:
    async_schedule(write_user_memory, state)   # 后台异步，不阻塞
    return {"memory_written": True}
```

| 钩子 | 位置 | 作用 |
|---|---|---|
| `inject_profile` | 意图识别前 | 检索注入当前用户画像 |
| `write_memory` | 回复生成后 | 异步写入/更新事实 |

## 6. 性能 / 合规 / 自托管运维考量

- **延迟**：写入走**异步**，检索走 Neo4j 图查询，均不占同步 <10s 预算
- **合规/被遗忘权**：删用户需在指定 `tenant_id` 内清理该用户实体及关联事实（`provenance` 便于定位）；删除租户则先停用，再按任务清理该租户全部图谱、向量和缓存。
- **审计**：每条事实带 `tenant_id`、来源（`source`）和操作者/任务 ID，可回溯到租户/工单/会话，满足留痕

**敏感画像治理（仅记录客观事实，不自动决策）**：
- **不存主观标签**：不写入"维权成瘾/高风险"等主观判断；只存可验证客观事实
- **访问控制**：涉及地址/历史计数等敏感画像，仅本租户客服/管理员可见，客户不可见；跨租户请求直接拒绝并留审计
- **删除权**：客户/法务可请求删除标签与关联记忆（被遗忘权），删除后同步清理图谱

**自托管运维成本（务必心里有数）**：
- Graphiti 是框架而非本项目现成服务，仍需实现租户作用域检索 API、后台任务、监控和失败处理。
- Graphiti 的默认匿名遥测不属于本项目数据面；但“完全自托管”仍要求显式关闭（`GRAPHITI_TELEMETRY_ENABLED=false`）并以出网规则/日志验证。该控制项也应纳入部署验收。
- 需要运维的组件至少包括 Neo4j、Graphiti 接入服务和本地 embedding/LLM 抽取端点；同时还会叠加 PostgreSQL、Milvus、Redis/Celery 与可观测组件。每项都需要版本固定、备份、告警和升级计划。
- 增量建图会产生 LLM/embedding 抽取负载，必须进入后台队列；数据量增长后需实测索引、查询延迟、存储增长和删除恢复。
- **分阶段闸门**：先完成单租户/双租户隔离验证和备份恢复演练，再决定是否把图谱接入主流程。未通过闸门时保留接口，不把长期记忆作为写操作判定依据。

## 7. 答辩叙事（可直接背）

> "长期记忆我用 **Graphiti（开源时序知识图谱）+ Neo4j** 自托管。工单画像的关键不是'记得'，而是'**某条事实在哪个时间区间为真**'——用户搬家后我仍要还原'他当时留的地址'来判断纠纷。Graphiti 是可独立获取和自托管的开源框架，本项目不依赖 Zep Cloud；但实际接入、租户过滤和故障恢复仍要在后续环境里验收。政策问答仍走 Agentic RAG（Milvus），图谱只管用户画像记忆层，且只记客观事实，不做主观风险判定。"

**高频追问应答**：
- *"为什么不用 Mem0？"* → 它覆盖旧事实、丢历史；我的需求是时序追溯。
- *"自托管会不会太重？"* → 是偏重（图库+引擎+embedding 三套），所以我先留接口做轻量验证，成熟后再上；写操作异步不阻塞。
- *"政策检索走图谱吗？"* → 不，政策问答仍走 Agentic RAG；图谱只做用户画像记忆层，分工明确。
- *"记忆里会不会有危险标签？"* → 原型不存主观风险标签，只存可验证客观事实；不基于记忆自动拒绝退款/退货。
