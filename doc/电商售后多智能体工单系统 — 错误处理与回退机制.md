# 电商售后多智能体工单系统 — 错误处理与回退机制（Error Handling & Fallback）

> **定位**：错误处理与回退专项设计，与《项目架构说明书 / 记忆架构设计 / 工具调用与集成 / 生产基线与验收测试》配套。
> **核心结论**：**安全优先 + 单一 LLM 接入 + 分层时效**。把**敏感写操作安全**（能力矩阵 + 幂等 + 审批 + 安全回退矩阵）做成最硬的差异化亮点，并按**对话实时 / 后台批处理**做时效分层。

---

## 1. 设计原则（为什么不是裸 try/except）

| 原则 | 说明 |
|---|---|
| **先分类再行动** | 重试 400 白烧预算、重试 429 加深节流、内容策略拒绝转多 provider 纯亏——错误必须先分类 |
| **一个 deadline，不加超时** | 每个请求一个总延迟预算，每个 attempt 花自己的份额，别让链 = 多份超时相加 |
| **副作用幂等** | 重试 / 中断恢复一律重放整节点，扣款、写库、发消息的节点**必须幂等**，否则重试=重复操作 |
| **先保证"不做错"，再谈"不出错"** | 高敏感（真金白银/隐私）下，宁可拒绝 / 转人工，**绝不幻觉化账户操作** |

---

## 2. 选型决策矩阵（基于本项目约束）

| 层 / 方案 | 本项目决定 | 理由 |
|---|---|---|
| 跨 provider / 多中转容灾（LiteLLM/OpenRouter 全链路） | ❌ 不做 | 本项目用**单一本地/内网 OpenAI 兼容端点**；容灾列为生产级增强项，但架构上预留网关扩展 |
| **能力矩阵**（写风险只许高可靠/审批路径） | ✅ **必做 + 亮点** | 退款/退货/改址是真钱/敏感信息，便宜模型绝不能碰写工具 |
| **写操作幂等**（防重复退款） | ✅ **必做** | retry/中断恢复最怕重复执行资金操作 |
| **写风险走 interrupt 人工审批** | ✅ **必做** | 退款/退货/改址一律审批，失败/低置信回退人工 |
| **降级阶梯**（收工具→RAG-only→带状态转人工） | ✅ **必做 + 亮点** | 高敏感下宁可拒答，不幻觉化资产操作 |
| 节点级容错（per-node timeout/error_handler/retry） | ✅ 上（对话路径） | 实时快速失败，批处理保守重试 |
| 健康门 / hedged request | ⚠️ 部分（仅实时短超时） | 不做 hedged（贵），用短超时 + 熔断 |
| 批处理回退（队列/死信/3 次重试） | ✅ 做 | 后台任务可耐心重试 + 入死信转人工 |

## 3. 分层设计

### 3.1 LLM 回退（单端点 · 简化版，只做 4 件事）

- **错误分类器**：429 → 退避重试（尊重 `Retry-After`）；5xx / 超时 → 降级；4xx / 内容拒 → 直接失败。
- **有界重试**：同一次 2 次，指数退避 + jitter。
- **熔断**：该端点连续失败（如 3 次/窗口）→ 快速降级，不再裸等。
- **总 deadline**：单请求 <10s，不叠加超时。

```python
RETRYABLE = {408, 409, 429, 500, 502, 503, 504}


def classify(e):
    if isinstance(e, (TimeoutError, ConnectionError)):
        return "reroute"
    if isinstance(e, APIStatusError) and e.status_code in RETRYABLE:
        return "retry_then_reroute"
    return "fail"
```

### 3.2 敏感写操作安全墙（本项目核心）

```python
# 能力矩阵：仅名单内的模型可触碰写操作工具。
# 判断依据为「模型名显式白名单」，而非分数阈值——本地/内网模型名可控，白名单比阈值更可复现。
HIGH_CONFIDENCE_MODELS = {
    "gpt-4",
    "gpt-4-turbo",
    "claude-3-opus",
    "qwen2.5-max",
}


def capability_ok(model: str) -> bool:
    """写操作门控：模型必须显式位于高置信名单，否则一律拒绝写并转人工。"""
    return model in HIGH_CONFIDENCE_MODELS


WRITE_RISK_ACTIONS = {"process_refund", "process_return", "update_return_address"}


def run_write_action(state):
    if not capability_ok(state["model"]):
        return route_to_human(state, "模型档位不足，转人工")
    require_tenant_context(state["tenant_id"])
    op_id = new_op_id(state["tenant_id"])  # operation_id（租户内业务唯一，幂等键）
    if executed(op_id):
        return replay(op_id)     # 已执行 → 重放，不重复
    return interrupt({...})      # 一律人工审批
```

三件套缺一不可：**能力矩阵（便宜模型禁写）+ 幂等操作 ID（不重复执行）+ 人工审批（interrupt）**。

> **能力矩阵规则**：写操作工具（`process_refund` / `process_return` / `update_return_address`）**仅允许** `HIGH_CONFIDENCE_MODELS` 名单内的模型调用；名单外的模型（含未登记的本地/开源小模型）一律拒绝写并转人工。判断依据是**模型名显式白名单**，避免依赖模糊的分数阈值或硬编码。读类/政策类查询（如 `query_order`、`retrieve_policy`）不受此限制，可在任意模型档位上执行。

#### 3.2.1 审批后执行面（Execution Engine）：shadow/live 状态机 + 补偿 + 回调验签 + 对账

审批通过后的 `execute_refund` / `execute_return` / `execute_address_update` 交给独立的**执行引擎**（`src/execution`），不再直接写库标记：

- **shadow 模式（默认，第一轮）**：只生成「待执行记录 + 模拟回执」（`executions` 表，`mode=shadow`，`receipt.simulated=true`），**绝不调用真实资金接口**；provider 为空。
- **受控执行开关（live）**：`execution_mode=live` 且显式配置 `FundsProvider` 才开启真实调用；live 无 provider 一律 fail-closed（503）。通过沙箱端到端验收后才允许翻到 live。
- **执行状态机**（`ExecutionStatus`，单向封闭，见 `can_transition`）：`pending_submit → submitted → confirmed / failed → compensated / human_handoff`，对账阶段再收口 `reconciled / mismatched`。终态后任何跃迁被拒（防重复扣款/退款）。
- **业务唯一幂等键**：`executions` 以 `operation_id` 为锚点（`UNIQUE(tenant_id, operation_id)`），复用操作的业务幂等键；重复请求/重复审批/重试只重放，绝不重复提交外部。
- **回调验签 + 重放保护**：外部回调以 `HMAC-SHA256(raw_body)` 验签；终态记录封闭、相同 `nonce` 只重放不重复生效、金额一致性校验；不一致 → `mismatched` + 转人工。
- **失败补偿**：外部明确失败/不确定时，以同一 `idempotency_key + execution_id` 发起 `provider.compensate`（回滚），补偿失败收敛到 `compensation_failed` + 转人工。
- **对账任务**：`engine.reconcile(tenant_id)`（Celery 任务 `execution.reconcile_tenant`）对非终态记录向外部查询真实状态收口，不一致 → `mismatched` + 转人工；`shadow` 记录已收敛为 `confirmed`，无遗留对账目标。

### 3.3 编排层：节点级容错

```python
builder.add_node("generate_response", gen,
                 timeout=TimeoutPolicy(deadline=10, idle=3),
                 error_handler=handle_node_error)
builder.add_node("process_refund", refund, retry_policy=RetryPolicy(max_attempts=2, backoff=exponential))
```

- `timeout=`：超时抛 `NodeTimeoutError`，清空该次写入，交给 retry policy，不留半状态。
- `error_handler=`：节点失败时补偿 / 路由到失败路径，而非让整 run 崩掉。
- `checkpointer`：长任务/中断后从断点恢复（durable execution），与 HITL 同一机制。
- 增强：节点级 `cache_policy`（结果缓存）、`graceful draining`（关机优雅排空）。

### 3.4 时效分层（对话实时 vs 后台批处理）

| 路径 | 策略 |
|---|---|
| **对话实时**（<10s 体验） | 短超时（deadline=10 / idle=3）、快速失败、降级为兜底话术 + 稍后转人工 |
| **后台批处理** | 保守重试 3 次（指数退避 + jitter）、队列、超时入**死信**转人工 |

> **降级边界**：实时路径降级只用于**政策问答/查询类**，绝不用于资金/敏感写操作；写操作降级一律 → 人工。这里的“转人工”不是一句泛化话术，而是保留 `operation_id`、当前状态、失败原因和审批上下文的受控移交。

### 3.5 降级阶梯（越下越保守）

```text
收工具集  →  缩短上下文  →  RAG-only 应答（仅政策/查询）  →  带完整状态转人工
（绝不：在降级路径上做任何资金/隐私写操作）
```

> 高敏感场景：转人工优于"用一个不可靠路径给出可能错误的账户操作"。

> **RAG-only 的边界**：它不是相关性或忠实度失败后的“换个名字继续答”。只有已验证来源仍可由确定性模板/引用式呈现时，政策/查询类才可使用 RAG-only；无文档、相关性重试耗尽、草稿缺失、幻觉检查失败或重试耗尽，均必须写入机器可读原因并 fail-closed 转人工。

### 3.6 写操作安全回退矩阵（必须实现）

| 触发条件 | 用户可见反馈 | 后台动作 | 审批/审计 |
|---|---|---|---|
| 模型不在白名单或能力校验失败 | “当前请求需要人工处理” | 不调用写工具；保留 `operation_id` 与已验证订单信息 | 创建人工工单，记录模型、租户、原因 |
| LLM 超时、429/5xx 或结构化输出失败 | “已记录申请，人工将继续处理” | 不执行写入；进入有界重试，超限进入死信/人工队列 | 通知审批人，记录 attempt、错误分类和 deadline |
| 金额、资格、地址或订单归属异常 | “信息需要人工核验” | 立即停止；冻结本次 `operation_id` 的自动执行 | 升级人工，保留异常字段摘要，禁止记录完整敏感值 |
| 审批超时或审批恢复失败 | “申请仍在人工审核中” | 保持 `pending`，禁止自动放行或重新生成新操作 ID | 提醒/升级审批人，记录超时与恢复结果 |
| 检查点/租户作用域校验失败 | “会话无法安全恢复，已转人工” | 拒绝继续执行，禁止使用默认租户或全局 checkpoint | 记录安全事件；必要时阻断租户写操作 |
| 审批通过后执行写库/提交接口超时 | “申请已提交，正在核对结果” | 以同一 `operation_id` 创建补偿/对账任务；不重复提交 | 记录提交状态、重试和最终对账结果 |

**硬规则**：写路径任何回退都不得切换到低档模型执行，不得跳过 `human_approval`，不得清除或重建原 `operation_id`。人工接手必须拿到最小必要状态：`tenant_id`、`thread_id`、`operation_id`、`approval_id`、业务意图、已验证事实、失败分类和下一步动作。

## 4. 各环节错误处理清单（映射到本项目节点）

| 节点/层 | 可能的错误 | 处理 / 回退 |
|---|---|---|
| `classify_intent` | LLM 超时/解析失败 | 超时→降级兜底意图；解析失败→重试 1 次→转 `handle_error` |
| `route_by_intent` | 意图低置信 | 置信 < 阈值 → 回退到 `escalate_ticket` 或直接问澄清 |
| `query_order` / `track_shipping` | 工具超时/查不到 | 重试→换等价工具→告知用户稍后再试→转人工 |
| `process_refund` / `process_return` / `update_return_address` | 金额/资格异常 | **能力矩阵门控 + 幂等 + interrupt 人工审批**；任何异常转人工 |
| `agentic_rag` | 检索不相关/幻觉 | 子图内有界自纠正 + 幻觉检测重生成；每次重生成都必须清空上一版答案草稿，且上一版答案不得作为证据。无文档、相关性重试耗尽、草稿缺失、检查失败或重试耗尽 → `falls_to_error=True` → 主图 `handle_error` → 透明转人工；不得输出未经验证草稿 |
| `human_approval` | 审批人无响应/超时 | 超时→提醒/自动升级；拒绝→记录反馈并终止，不执行 |
| `generate_response` | 生成失败 | per-node timeout + error_handler → 降级兜底话术 + 转人工 |
| 记忆写入（Graphiti/Neo4j） | 图库卡顿/写入失败 | 异步 + 失败重试 + 死信；**不阻塞对话** |

## 5. 幂等设计（写操作）

**幂等键必须是"业务操作唯一标识"，绝不含重试次数/attempt**——否则每次重试生成新 ID，同一笔资金业务可能重复执行。

- **幂等键**：由**租户内业务事实**决定、与执行次数无关，如 `oprefund:{tenant_id}:{order_id}:{refund_request_id}`、`opreturn:{tenant_id}:{order_id}:{return_request_id}`、`opaddr:{tenant_id}:{order_id}:{address_change_request_id}`。同一业务重试复用同一键。
- **唯一约束 + 原子写入**：业务表建 `UNIQUE(tenant_id, idempotency_key)`；执行用 `INSERT ... ON CONFLICT (tenant_id, idempotency_key) DO NOTHING` 或事务内"检查+写入"。
- **执行前查** `executed(op_id)`，已执行则直接返回结果（重放），不重新执行。
- 用于 retry、interrupt 恢复、重复点击、审批通过后的提交——同一资金操作永不重复执行。

```python
op_id = f"oprefund:{tenant_id}:{order_id}:{refund_request_id}"
cur.execute(
    "INSERT INTO refund_ops(tenant_id, op_id, state) VALUES(%s,%s,'pending') "
    "ON CONFLICT (tenant_id, op_id) DO NOTHING",
    (tenant_id, op_id))
if cur.rowcount == 0:
    return load_existing_result(op_id)
```

## 6. 可观测与告警

- **指标**：fallback hit rate（降级触发率）、熔断事件（circuit open）、降级 tick、p95 延迟。
- **告警**：fallback hit rate > 5%（5 分钟窗口）≈ 主路径在退化；熔断卡在 open > 10 分钟 ≈ 持续故障。
- **故障注入演练**：staging 里 revoke key / 黑掉 endpoint / 注入 429/503，验证分类器决策、降级耗时、告警触发——别让回退路径的第一次执行发生在生产事故里。

## 7. 关键决策说明

> "我的场景是售后工单 + 真金白银，所以把力量压在安全这一维：能力矩阵让便宜模型永远碰不到退款/退货/改址；写操作幂等用操作 ID 确保 retry 或中断恢复绝不重复执行一次资金操作；所有写风险走 interrupt 人工审批；系统真扛不住就走降级阶梯——但降级只用于政策/查询类，写操作一律带完整状态转人工，绝不幻觉化给一个错误的账户操作。实时路径用快速失败保 <10s，后台任务才用耐心重试。核心是：先保证'不会做错资金操作'，再谈'尽量不出错'。"

**高频追问应答**：
- *"为什么不做跨 provider 回退？"* → 当前用单一本地/内网端点，瓶颈是业务安全不是 provider 可用性；跨 provider 列生产增强项。
- *"重试会不会重复退款？"* → 写操作全部走幂等操作 ID + interrupt 审批，重试/恢复只重放不重执行。
- *"系统挂了怎么办？"* → 对话路径降级为兜底话术 / 转人工，批处理入死信转人工；绝不把风险暴露给用户。
- *"便宜模型会不会被用来退款？"* → 能力矩阵直接禁止写风险工具在低档路径；写操作只许高可靠模型 + 审批。
