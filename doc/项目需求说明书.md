## 1. 项目概述

### 1.1 项目名称

**电商售后多智能体工单系统（E-commerce After-Sales Multi-Agent Ticket System）**

### 1.2 项目背景

电商行业售后场景存在大量重复性、规则明确但流程复杂的工单处理需求（退货、退款、物流查询、投诉等）。传统人工处理效率低、成本高，而单一 LLM 应用缺乏流程控制和多角色协作能力。多智能体系统可将规则明确的流程交给 Agent 自动编排，把需要判断资金、资格或人身隐私的环节交给人工审批，形成"自动处理 + 关键步骤人工兜底"的闭环。

### 1.3 项目目标

构建一个以**生产级能力为目标**的电商售后多智能体系统设计。当前交付物为设计文档；只有完成线上预发布、故障恢复和容量验收后，系统才可被称为生产就绪。设计具备：

- **自主处理**：自动处理退货、退款、物流查询等售后工单
- **安全可控**：敏感操作（退款、退货、改地址）一律人工审批
- **可观测可评估**：自托管全链路追踪 + 量化评估体系
- **可扩展**：模块化设计，支持新增业务场景
- **数据可控**：LLM、数据、图谱、向量库和可观测均由项目方自部署、自管理；可运行于自管机房或项目账户下的租赁 IaaS，不依赖公有 SaaS
- **租户隔离**：以服务端认证的 `tenant_id` 为订单、工单、会话、记忆、知识、审批和审计的最小边界，跨租户默认拒绝

### 1.4 目标用户

- **电商运营人员**：使用系统处理售后工单
- **客服管理员**：审批敏感操作、监控系统运行
- **开发者**：扩展和维护系统

## 2. 功能需求

### 2.1 核心功能

| 功能模块 | 优先级 | 描述 |
| :--- | :--- | :--- |
| 售后意图识别 | P0 | 识别用户问题类型（退货/退款/物流/政策咨询/投诉） |
| 订单信息查询 | P0 | 根据订单号查询订单状态、金额、商品信息 |
| 物流状态追踪 | P0 | 查询并返回最新物流信息 |
| 退货政策问答 | P0 | 基于知识库回答退货政策相关问题 |
| 退款处理 | P1 | 处理退款申请，一律触发人工审批 |
| 退货申请 | P1 | 处理退货申请，与改地址分离，触发人工审批 |
| 退货地址变更 | P1 | 修改退货地址，触发人工审批 |
| 工单升级 | P2 | 复杂问题转交人工客服 |
| 多轮对话 | P2 | 支持上下文连续对话 |

### 2.2 非功能需求

| 需求类型 | 具体要求 |
| :--- | :--- |
| 响应时间 | 以批准的业务 SLO 为准；单次请求 < 10 秒仅作为后续压测目标，非当前实测结论 |
| 可用性 | 支持断点续跑，故障后可恢复；生产目标以多副本、RPO/RTO 和恢复演练验收 |
| 可观测性 | 自托管全链路追踪，记录每步决策和 Token 消耗 |
| 评估体系 | 支持自动化评估（准确率、解决率、延迟） |
| 安全性 | 敏感操作一律人工审批，操作留痕、幂等 |
| 多租户 | 服务端解析租户上下文；业务库、检查点、缓存、队列、向量和图谱按 `tenant_id` 隔离 |
| 数据可控 | 完全自托管；部署到租赁 IaaS 时，数据仅在项目方控制的服务器、网络和备份边界内流转，不使用公有 SaaS |

## 3. 技术需求

### 3.1 技术栈要求

- **核心框架**：LangGraph（流程编排 + 状态管理）+ CrewAI（子智能体执行）
- **RAG**：Agentic RAG（自纠正检索）+ LangGraph RAG（状态机编排）
- **长期记忆**：支持对用户跨会话行为的时序追溯与关联分析（用户画像、历史工单、事实随时间演进），据此选用 Graphiti + Neo4j（见《记忆架构设计》）
- **可观测性**：自托管 Langfuse（链路 + 指标），可选 Prometheus/Grafana；默认不依赖外部 SaaS
- **数据层**：PostgreSQL（业务/工单/检查点）+ Milvus（开发/预发布为固定版本 standalone，生产目标为 distributed/cluster）+ Neo4j（记忆图谱；生产可用性方案按版本与许可冻结）
- **异步队列**：Celery + Redis（Broker），全 Python 技术栈；不采用 Node/JS（BullMQ）方案
- **部署**：Docker Compose（开发验证）+ FastAPI；租赁服务器上的线上预发布验证；生产前后端分离、多副本与灾备要求见《生产基线与验收测试》

### 3.2 技术约束

- 全部代码开源，统一使用 **CPython 3.12.x**（开发、CI、容器运行时保持一致；不使用 Python 3.13）
- 支持 OpenAI 兼容接口的 LLM；完全自托管时接入项目方自管的本地/内网 OpenAI 兼容端点（vLLM/Ollama 等）。租赁 IaaS 部署时，模型端点须处于同一受控私网/安全组，不能将 prompt/响应转发到未批准的公有 SaaS
- 数据模拟生成，不依赖真实电商 API
- 前端采用 React + Next.js；异步队列仅用 Celery，不混用 Node

## 4. 项目范围

### 4.1 包含范围

- 完整的 LangGraph 主控图（意图识别 → 路由 → 审批 → 执行 → 回复）
- 3 个 CrewAI 子智能体（订单查询、物流追踪、退款处理），外加退货/改址业务工具
- Agentic RAG 模块（查询改写 → 检索 → 评分 → 自纠正闭环）
- 完全自托管的可观测性体系（Langfuse 自部署 + 指标）
- 评估测试集（不少于 50 个测试用例）
- React + Next.js 前端（生产界面）；后端 FastAPI
- 多租户基础设施：租户/成员关系、租户上下文、数据面隔离与跨租户拒绝测试
- 线上预发布验证计划：使用项目账户下租赁服务器验证 TLS、部署、至少两个租户隔离、故障恢复、备份恢复、压测与告警

### 4.2 已知边界（原型交付；生产目标项见《生产基线与验收测试》）

- 真实电商平台 API 对接（原型用模拟数据；生产目标接入真实 API）
- 生产级高可用部署尚未实施：K8s/等效编排、负载均衡、多副本、Redis HA、PostgreSQL 主备、Milvus distributed/cluster、备份恢复和 RPO/RTO 演练均为生产目标项
- 完整的租户生命周期治理、配额与独立 schema/数据库策略（当前实施共享库 + RLS/等效 guard 的基础隔离）
- 真实支付通道（原型仅写库标记 + 可替换提交接口；生产目标接入真实支付 + 对账补偿）
