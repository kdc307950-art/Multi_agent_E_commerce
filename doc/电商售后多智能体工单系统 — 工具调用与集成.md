# 电商售后多智能体工单系统 — 工具调用与集成

> **定位**：本文档是「项目架构说明书」的工具层专项，覆盖**工具调用规范选型、工具清单、工具组织方法论**三部分，并落到本项目的最终选型。
> **核心结论**：工具调用规范选 **MCP**（主流标准）；工具集为业务 7 + 平台 2，共 9 个工具能力；**工具组织采用「合并 → 分域 → 检索」三阶梯，本项目停在第二阶梯（子智能体分域）+ 静态绑定即最优**。

---

## 1. 工具调用规范选型

### 1.1 "是否统一"要分两层看

| 层次 | 是否统一 | 结论 |
|---|---|---|
| **规范/协议层**（怎么调） | ✅ **选 MCP** | 模型无关、可插拔、面向生态；是否"已过主流门槛"应结合官方生态与自身场景判断 |
| **模型侧原生机制** | 并存 | Function Calling 与 MCP **共存**：MCP 管"发现+传输+认证"，Function Calling 是模型吐结构化调用的底层能力 |
| **调哪些工具**（工具集） | ❌ **场景化，不统一** | 电商/律所/IT 工单各不相同，由本项目自行定义 |

> 一句话：**统一在"怎么调"，不统一在"调什么"。**

### 1.2 本项目的三层选择

| 层 | 选型 | 理由 |
|---|---|---|
| 协议层 | **MCP**（主） | 模型无关、未来接真实电商 API 无缝、便于说明 |
| 编排层 | **LangGraph 主控 + CrewAI 子智能体** | 状态机 + 角色化协作，工具绑定进节点 |
| 简单内部函数 | **原生 Function Calling** 兜底 | 本地 mock、延迟敏感，不必都包成 MCP |

> 结论：**规范选 MCP，但不必为 MCP 而 MCP**——可复用/跨模型/接第三方的包成 MCP server，小工具直接绑定。

## 2. 本项目工具清单

### 2.1 业务工具（对应功能需求 P0-P2）

| 工具 | 触发意图 | 敏感操作 | 暴露方式 |
|---|---|---|---|
| `query_order`（订单状态/金额/商品） | order | 否 | MCP server |
| `track_shipping`（物流轨迹/预计送达） | shipping | 否 | MCP server |
| `process_refund`（退款 eligibility + 金额 + **触发审批**） | refund | ✅ 人工审批 | MCP server |
| `process_return`（退货申请 eligibility + **触发审批**） | return_request | ✅ 人工审批 | MCP server |
| `update_return_address`（改退货地址 + **触发审批**） | return_address | ✅ 人工审批 | MCP server |
| `retrieve_policy`（政策解读） | policy/complaint | 否 | 走 Agentic RAG（自纠正） |
| `escalate_ticket`（转人工/升级） | complaint | 否 | MCP server |

> **已接入主图（设计态）**：`refund → process_refund → human_approval → execute_refund`；`return_request → process_return → human_approval → execute_return`；`return_address → update_return_address → human_approval → execute_address_update`。三种敏感操作**均进入唯一审批节点，无 direct 绕过**。

### 2.2 平台工具（横切，非业务但必须）

| 工具 | 用途 | 归属 |
|---|---|---|
| `query_user_profile` / `write_user_memory` | 长期记忆读写（Graphiti + Neo4j，记客观事实） | 记忆层 |

> `retrieve_policy` 已在上方业务工具表中计为 1 个业务工具；RAG 层复用该能力时不再重复计数。平台工具仅计 `query_user_profile` 与 `write_user_memory` 两项。

> 底层数据：`mock_db/orders.json`、`knowledge_base/*.md`（当前为模拟数据，未来可换真实电商 API）。

### 2.3 多租户工具契约

所有业务工具和平台工具在运行时都接收由服务端注入的 `TenantContext`，至少包含已验证的 `tenant_id`、`user_id`、当前租户角色和请求/追踪 ID。

- 客户端和模型**不能**在工具参数中指定或覆盖 `tenant_id`；工具 schema 不暴露可自由填写的租户字段。
- 工具执行前按 `tenant_id` 校验订单、工单、会话、审批单和操作单归属；任一资源不匹配直接拒绝并审计。
- 工具返回值必须限制在当前租户最小必要字段，不能把其他租户数据回灌到模型上下文。
- MCP server、内部函数、队列任务和重试任务都要重新验证租户作用域，不能仅依赖上游提示词或缓存。
- 租户停用、成员撤销或租户上下文缺失时，读写工具都快速失败；敏感操作同时转人工处理。

## 3. 工具组织方法论：三阶梯（核心）

工具一多，静态全量绑定会**上下文爆炸 + 模型选错**。解法是一条**阶梯式**路径，不是单点方案：

```text
第一阶梯  工具设计纪律（把"工具写得少而准"）   —— 最便宜，先做
    ↓
第二阶梯  分层 / 子智能体分域（把工具拆开）    —— 开源主流默认
    ↓
第三阶梯  动态工具检索（达到门槛才用）        —— 单 agent 巨量工具才需要
```

### 3.1 第一阶梯：工具合并与设计纪律

把细粒度工具**合并为 action 参数化**的工具，减少候选数量：

```text
原：list_open_orders / list_closed_orders / list_draft_orders   （3 个）
改：list_orders(state: 'open' | 'closed' | 'draft')             （1 个）
```

- 效果：减少近义工具候选，降低模型选择负担；具体合并比例以实际场景为准，不作外部指标承诺。
- 原理：让模型的选择任务从"从近义工具里挑"变成"选一个动作动词"，参数承载变化。

### 3.2 第二阶梯：分层 / 子智能体分域（开源主流做法）

按职能给**每个子智能体绑定自己的小工具集**（工具集隔离），避免单 agent 绑一堆。这是 LangGraph/CrewAI 等主流框架的核心机制：

| 框架 | 分域机制 |
|---|---|
| LangGraph | `langgraph-supervisor` + Deep Agents `task`（子代理隔离上下文） |
| CrewAI | `allow_delegation=True`（自动生成 Delegate work / Ask question） |
| OpenAI Agents SDK | `agent.as_tool()` / Handoff |
| Google ADK | `sub_agents`（Sequential/Parallel/Loop） |
| smolagents | `managed_agents` |

> 本项目天然分域：**3 个 CrewAI 子智能体**（订单/物流/退款）+ 退货/改址业务工具，主控 LangGraph 做路由。

### 3.3 第三阶梯：动态工具检索（达到门槛才用）

**Anthropic Tool Search Tool**：机制为工具打 `defer_loading: true` 不载入初始 prompt，只载入 Tool Search Tool + 3-5 个常驻工具；模型按需用 regex/BM25 搜目录，返回 `tool_reference`，API 自动展开。

**官方门槛（何时才该用）**：
- ✅ 该用：**≥10 工具 / 定义 >10k token / 选择精度下降 / 多 MCP server（200+）**
- ❌ 别用：**<10 工具 / 每请求都用 / 定义 <100 token**（普通 tool calling 更合适）

> ⚠️ **Tool Search Tool 是 Anthropic 专有、锁在 Claude Code**。开源替代：embedding 检索（RAG over tool registry）、BM25（`verantyx/tool-search-oss`）、混合（SCOUT，BM25+dense RRF）。具体效果需按自身工具规模实测。

### 3.4 兜底阶梯（场景再放大时才需要）

| 手段 | 适用 | 关键点 |
|---|---|---|
| ③ 动态检索 | 单 agent 巨量工具 | 上文 |
| ④ namespace 前缀（`mcp__github__create_pr`） | 跨 vendor 多 server 同名冲突 | 消命名冲突 |
| ⑤ MCP Gateway | >5 个 MCP server | ⚠️ 只聚合=把问题上移，必须主动 curate 每 agent 所见 |
| ⑥ Code Mode / Programmatic Tool Calling | 海量 API 端点 | 不暴露端点，给 `search()`+`execute()` 让 agent 在 sandbox 执行 |

## 4. 本项目的最优选择（结论）

实际状况：**业务 7 + 平台 2，共 9 个工具能力**，且已天然分到 3 个 CrewAI 子智能体 + 退货/改址工具（每个 2-3 个）。

**结论：停在第二阶梯 + 静态绑定 = 最优，第三阶梯动态检索（Tool Search）不需要。** 原因：
1. **没到门槛**：工具 <10 个，用普通调用；保留少量动态检索能力作为后续扩展点
2. **已分域**：子智能体各绑 2-3 个工具，自然拆分，不存在"单 agent 绑一堆"
3. **上 Tool Search 是负优化**：多一层检索延迟，却省不了 token（个位数工具本就不占多少），还加复杂度

**设计说明（反直觉但更稳妥）：**
> "工具检索（Tool Search）本质是给单 agent 绑几百上千工具的场景用的；我的工具只有 9 个，而且已通过三个 CrewAI 子智能体按职能分域、每个只绑 2-3 个工具，所以用静态绑定就是最优——工具一多反而降智费 token，与其动态搜，不如在架构上把工具拆开。这比盲目上 Tool Search 更懂工程权衡。"

## 5. 安全 / 合规注意

- **协议授权不等于业务授权**：MCP 只定义传输/发现协议，**协议层认证授权不能替代应用层 RBAC、订单归属校验与逐工具策略**。
- **严格 schema**：工具调用用 `strict: true`（OpenAI）或等价 schema 校验，防畸形调用。
- **输出验证**：工具返回值先校验再回灌模型上下文。
- **运行时拦截**：工具执行前拦截，接自托管 Langfuse 审计留痕。
- **租户拦截**：工具执行前强制校验服务端 `tenant_id` 与资源归属；数据库/RAG/图谱/缓存/队列均不得使用无租户作用域的查询或 key。
- **敏感工具（退款/退货/改址）必须走唯一 `human_approval` interrupt**，别信任模型自主决定。
- **记忆注入最小化**：长期记忆只注入当前会话可用的客观事实，不注入主观风险标签，也不据此自动拒绝。
