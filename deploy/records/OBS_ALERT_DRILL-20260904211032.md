# 观测告警演练报告（生产 · after-sales-prod）

> 演练编号：OBS-ALERT-20260904211032 · 目标：production(after-sales-prod) 观测链路
> 执行人/复核人：`captain(deploy-engineer)` / `security-auditor`
> 依据：`deploy/observability/alert-rules.yml`(15 条,单一权威)+ `alertmanager.yml` + 运行态 Prometheus/Alertmanager/webhook sink 实测。

---

## 1. 链路构成（已就绪）
| 组件 | 说明 |
|------|------|
| Prometheus | `after-sales-observability-prometheus-1`(v2.53.0),经 prod-net 抓 `job=api_prod`(after-sales-prod-api-1:8000/api/metrics),`rule_files` 加载唯一权威 `alert-rules.yml`(15 条) |
| Alertmanager | `after-sales-observability-alertmanager-1`(v0.27.0),`prometheus.yml alerting`→`alertmanager:9093`;`/api/v1/alertmanagers` active=[alertmanager:9093] |
| 通知通道(自托管) | `after-sales-observability-alert-webhook-sink-1`(python:3.12-alpine 跑 `evidence/mock_webhook_receiver.py`),webhook 接收端落盘 `/data/inbox.jsonl`(obs 网内,无外发 SaaS) |

## 2. 触发（Firing）
触发方式:把备份恢复 gague `drill_rpo_seconds{component="pg_backup"}` 临时写为 **1200**(>900)与 `drill_rto_seconds`=**4000**(>3600)(经 `deploy/scripts/drill_metric_exporter.py write`,`deploy/drills/metrics/drill_gauges.json`,由 api `/api/metrics` 合并采集)。

Prometheus `/api/v1/alerts`(实测):
```
RpoExceeded  state=firing  value=1.2e+03  severity=critical  job=api_prod  instance=after-sales-prod-api-1:8000
  summary=“RPO 超阈值（>15min）”  activeAt=2026-09-04T13:05:54Z  (for:1m 后触发)
RtoExceeded  state=firing  value=4e+03  severity=critical  job=api_prod  instance=after-sales-prod-api-1:8000
  summary=“RTO 超阈值（>60min）”
```
→ **关键告警成功触发**。

## 3. 定位 / 路由（Alertmanager）
Alertmanager `/api/v2/alerts`(实测)：`RpoExceeded`、`RtoExceeded` 均 `status.active`、`receivers=[{"name":"alert-webhook"}]`、`generatorURL=http://…:9090/graph?g0.expr=drill_rpo_seconds{component="pg_backup"}>900 …`(可直接定位到触发表达式与来源实例,job=api_prod)。`alertmanager.yml` 路由按 `severity=critical` 命中 `alert-webhook`，`send_resolved=true`。

## 4. 通知（自托管 webhook sink）
`alert-webhook-sink` 收到 webhook 并落盘 `/data/inbox.jsonl`(实测)：`receiver=alert-webhook`、`status=firing`、含 `RpoExceeded`/`RtoExceeded` 完整告警体(labels=job=api_prod, instance=after-sales-prod-api-1:8000, severity=critical)。→ **触发→路由→通知 闭环成立**。另收到 deploy t4 的合成告警 T4WebhookChannelCheck/T4WebhookChannelCheck2 亦命中(等价通知通道验证)。

## 5. 恢复（Resolve）
把 gauge 回写为 `rpo=12.6`、`rto=2.0`(低于阈值,经 `drill_metric_exporter.py`)。
- Prometheus `/api/v1/alerts` → **空**(RpoExceeded/RtoExceeded 已 resolve)。
- Alertmanager `/api/v2/alerts` → RpoExceeded/RtoExceeded 已移除(仅剩 t4 合成告警)。
- `drill_rpo_seconds=12.6`(job=api_prod)实测回到健康值。
- 注:alertmanager 的 `resolved` webhook 通知按 `group_interval=5m` 分组时序稍后下发(send_resolved=true 已配置);**告警恢复本身已达成**(Prometheus 告警清空 + Alertmanager 移除)。

## 6. 结论
- **关键告警能触发**:是(RpoExceeded/RtoExceeded 在 `job=api_prod` 生产指标上 firing,critical)。
- **关键告警能定位/路由**:是(Alertmanager receivers=[alert-webhook],generatorURL 定位到触发表达式与来源实例)。
- **关键告警能通知**:是(自托管 webhook sink 收到 firing 通知并落盘)。
- **关键告警能恢复**:是(gauge 回落后 Prometheus 告警清空、Alertmanager 移除;系统回到健康态)。
- 说明:Alertmanager 与通知通道为自托管(obs 内网,无外发 SaaS),满足宪法完全自托管红线;`ApiHighErrorRate` 已按 job/route/method 分维,避免 preview+prod 混算。
